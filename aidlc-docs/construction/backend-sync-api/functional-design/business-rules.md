# Business Rules: Backend Sync API

## アカウント（Q1回答: 事前プロビジョニング）
- 公開の新規登録エンドポイントは提供しない
- アカウント（email + パスワードハッシュ）はセットアップ時に環境変数またはセットアップスクリプトで1件作成する

## パスワードポリシー（SECURITY-12）
- 最小8文字
- アダプティブハッシュアルゴリズムで保存（平文・弱いハッシュは禁止）

## セッション管理（SECURITY-12）
- 有効期限30日間、スライディング（アクセスごとに延長）
- ログアウトで該当セッションを即時失効（レコード削除）
- セッションIDはhttpOnly・Secure・SameSite属性付きCookieで配布する

## ブルートフォース対策（SECURITY-12）
- ログイン連続失敗時に段階的な遅延を導入する

## 曲データの入力検証（SECURITY-05）
- `songKey`: `local:<64桁16進数>` または `yt:<11文字>` の形式のみ受け入れる
- メモ: 最大2000文字
- ループ区間: `0 <= a < b <= 86400`（曲の長さはサーバーが知らないため、24時間を粗い上限として使う。正確な範囲チェックはフロントエンドの責務）

## 書き込み競合処理（Q2回答: サーバーでLast-Write-Wins強制）
- `PUT /songs/{songKey}`のリクエストボディの`updatedAt`が、サーバーに既存のレコードの`updatedAt`より**厳密に小さい**場合、409 Conflictを返し、レスポンスボディに現在のサーバー側の最新データを含める
- `updatedAt`が既存と同じか新しい場合は上書きを受け入れる（同一内容の再送は冪等に成功する）

## 認可（SECURITY-08）
- 全ての`/songs/*`エンドポイントは、Cookieのセッションから解決した`userId`でスコープする
- リクエストで指定された`songKey`が他ユーザーのものであっても、存在しないものとして扱う（404）。他ユーザーの存在を推測できる情報を返さない

## 未実装・対象外
- 公開の新規登録（Q1回答により対象外）
- 曲データの削除API（v1のストーリーに削除要求はないため未実装。必要になれば将来追加）
